### 2026-07-27/28 — Phase 0: FastAPI + Postgres + Alembic working end to end

**Built:**
- Python venv + `pyproject.toml` as the single dependency/tool-config manifest (no `requirements.txt`).
- Minimal FastAPI app (`app/main.py`) with `/` and `/health`, run via `uvicorn app.main:app --reload`.
- Postgres running locally via Docker Compose, with a named volume for persistence.
- `pydantic-settings`-based config (`app/core/config.py`) reading `DATABASE_URL` from `.env`.
- Async SQLAlchemy engine + session factory (`app/db/session.py`), declarative `Base` (`app/db/base.py`).
- First real model, `User` (`app/models/user.py`), with a sync-driver Alembic setup (`psycopg2`
  for migrations, `asyncpg` for the app at runtime — migrations don't need to be async).
- First migration generated and applied — `users` table now exists for real in Postgres.

**Learned:**
- Virtual envs isolate per-project dependencies; `pyproject.toml` (PEP 621) is the modern
  single-file replacement for `requirements.txt` + scattered tool configs.
- FastAPI defines routes/logic; Uvicorn is the ASGI server that actually listens on a port and
  runs it — always run FastAPI *through* an ASGI server, never standalone.
- `pydantic_settings.BaseSettings` only reads `.env`/env vars once **instantiated**
  (`Settings()`), not off the class itself — a very easy mistake to make.
- SQLAlchemy's **engine** manages the connection pool (created once); a **session** is one
  request's unit of work (opened, used, closed) — never shared across requests.
- Alembic's `env.py` needs an explicit `sys.path` fix to `import app...`, since running the
  `alembic` console script doesn't add the current directory to `sys.path` the way `python -m`
  or `uvicorn` does.
- `target_metadata = Base.metadata` is what makes `--autogenerate` actually see your models —
  and every model needs to be *imported* somewhere Alembic's `env.py` runs, or it won't be
  registered on `Base.metadata` at all.
- Docker named volumes persist data outside a container's lifecycle; without one, `docker
  compose down` silently wipes everything.
- **Postgres env vars (`POSTGRES_USER` etc.) only take effect the very first time it initializes
  an empty data directory** — changing them later does nothing until you wipe the volume
  (`docker compose down -v`) and let it reinit.
- Always review an autogenerated Alembic migration before running it — autogenerate is a diffing
  heuristic, not infallible (can misread renames as drop+add, miss server-side defaults, etc.).

**Gotchas that cost real debugging time (worth remembering):**
- A file saved as `"pyproject.toml  "` (trailing spaces in the filename) is a *different file* to
  the OS than `pyproject.toml` — pip couldn't find it and errored as if it didn't exist.
- TOML arrays need commas between every entry, same as Python/JSON lists — a missing comma threw
  a cryptic `TOMLDecodeError: Unclosed array`.
- `setuptools` auto-discovers "packages" in a flat layout and refuses to build if it finds
  multiple top-level candidates (`app/` and `alembic/` both looked like packages to it) — fixed
  with `[tool.setuptools] packages = []`, since this project was never meant to be an installable
  library in the first place, just a runnable app.
- `configparser` (which `alembic.ini` uses) treats `%` as its own interpolation syntax — a
  URL-encoded password containing a literal `%40` broke it. Fix: escape as `%%` in *that specific
  file only* (not an issue in `.env`, which uses a different parser).
- Pylance flags `Settings()` as "missing argument" for required fields with no default — a known
  false positive with `pydantic-settings`, since static analysis can't see that values get filled
  from `.env` at runtime instead of constructor args. Harmless; safe to `# type: ignore[call-arg]`.
- Running `uvicorn` from the wrong working directory (`GymTracker/` instead of `GymTracker/backend/`)
  gives `ModuleNotFoundError: No module named 'app'` — Python can only find `app/` as a package
  relative to the current directory.
- **A pre-existing native Postgres install on the Mac was already bound to `127.0.0.1:5432` and
  `[::1]:5432`**, silently intercepting every "connect to localhost:5432" attempt meant for the
  Docker container — which was actually fine the whole time. Diagnosed with
  `lsof -iTCP -sTCP:LISTEN -n -P | grep 5432`; fixed by remapping Docker's host port to `5433`
  instead of touching the native install.

### 2026-07-28 — Phase 0 closed out: Flutter scaffolded, first screen talks to the backend

**Built:**
- Flutter SDK installed (via `brew install --cask flutter`); Android/iOS toolchains skipped for
  now (no Android Studio/Xcode yet) — developing against the **Web** target only, which needs
  nothing beyond Flutter itself and Chrome.
- `frontend/` scaffolded with `flutter create --platforms=ios,android,web .`.
- Added `dio` (the HTTP client from [03-tech-stack.md](03-tech-stack.md)) to `pubspec.yaml`.
- Added `CORSMiddleware` to the FastAPI backend (`app/main.py`) so a browser-based Flutter Web
  app is actually allowed to call it.
- Replaced the default counter demo in `lib/main.dart` with a real screen (`HealthCheckScreen`)
  that calls `GET /health` on the backend and renders the result — closing the loop the Phase 0
  roadmap set out ("one real endpoint, one real screen that calls it").

**Learned:**
- Dart is the language, Flutter is the framework+SDK built on it — installing Flutter bundles
  Dart automatically, no separate install.
- `pubspec.yaml` is Dart/Flutter's dependency manifest — direct equivalent of `pyproject.toml`;
  `flutter pub get` is the equivalent of `pip install`.
- Everything on screen in Flutter is a **widget**. `StatelessWidget` = "looks the same given the
  same inputs, no memory of its own" (vs. `StatefulWidget`, not needed yet). Every widget
  implements `build()`, which returns more widgets — this nesting is the "widget tree."
  `runApp(widget)` mounts one widget as the root of the whole app.
- Dart's `Future<T>` + `async`/`await` is the same concept as Python's `async def`/`await` — a
  `Future` is a promise of a value that isn't ready yet.
- `FutureBuilder` ties a one-shot async call (like an HTTP request) to what gets rendered,
  without needing `StatefulWidget`/`setState` — its `builder` callback re-runs as the future's
  state moves from "waiting" to either an error or real data (`snapshot.connectionState`,
  `snapshot.hasError`, `snapshot.data`).
- **CORS**: browsers block a page from calling an API on a different origin (even just a
  different port counts) unless the server explicitly opts in via response headers — necessary
  for any browser-based client (Flutter Web included) talking to a separately-run API, even on
  the same machine.

**Gotchas:**
- `flutter create` **never overwrites a file that already exists** — it only fills in what's
  missing. This repo had pre-existing empty placeholder files (`pubspec.yaml`, `lib/main.dart`)
  from the initial project skeleton, so `flutter create` silently skipped regenerating them,
  leaving blank files that broke everything downstream (no SDK constraint, no `main()` function)
  until they were deleted and `flutter create` was re-run.
- A stray duplicate `tests/` folder (plural) existed alongside the real `test/` Flutter
  generates — leftover from the same pre-existing skeleton, removed to avoid confusion.
- A URL string missing its scheme (`'localhost:8000/health'` instead of
  `'http://127.0.0.1:8000/health'`) fails at the network layer with a vague
  `DioException [connection error]` — the browser can't tell it's meant to be an absolute network
  address without `http://`.
